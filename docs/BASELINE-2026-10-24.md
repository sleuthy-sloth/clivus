# Baseline — Linux arm64 dev host, 2026-10-24

Unit 0 of `docs/PLAN-EXECUTION.md`. This records what actually runs, so later units can be verified
instead of asserted.

## Host

| | |
|---|---|
| Machine | Raspberry Pi (aarch64), 4 cores, 7 GB RAM |
| OS | Debian 13 (trixie), kernel 6.18.34+rpt-rpi-2712 |
| Compiler | GNU 14.2.0 |
| CMake | 3.31.6 (preset `linux`, generator Ninja) |

| DCMTK | 3.6.9 (Debian `libdcmtk-dev`) |

This host is **not** a supported release target: Clivus ships macOS and Windows. It is used to
compile and run the tests, not to judge GUI rendering, DPI, or GPU behaviour. Any claim about how
something looks still needs a human on macOS or Windows.

## Commands

```
cmake --preset linux-core && cmake --build --preset linux-core
ctest --preset linux-core --output-on-failure

cmake --preset linux        && cmake --build --preset linux
ctest --preset linux --output-on-failure
```

`linux` and `linux-core` presets were added in this unit; the repo previously had macOS and Windows
only. `linux-core` sets `CLIVUS_BUILD_APP=OFF`, so core work verifies in about a minute.

## Two host fixes required to build at all

1. **DCMTK 3.6 vs 3.7 tag constant.** `core/src/anonymize.cpp` used `DCM_EthnicGroups`, which exists
   in DCMTK 3.7 (what Homebrew ships) but not 3.6.9 (Debian). Replaced with the explicit
   `DcmTagKey(0x0010, 0x2160)`, matching the raw-tag style already used in that array. Same tag,
   no version `#if`.
2. **DCMTK's link interface needs `libtiff-dev`.** Debian's `DCMTKConfig.cmake` links
   `/usr/lib/aarch64-linux-gnu/libtiff.so`, which only `libtiff-dev` provides; without it Ninja
   fails with "missing and no known rule to make it". Host package, not a repo change.

## Baseline test result — app lane

The full GUI build (199 targets, Qt 6.8.2 from Debian) links clean, and every test runs headless
with the offscreen QPA plugin:

```
QT_QPA_PLATFORM=offscreen ctest --test-dir build/linux --timeout 90

100% tests passed, 0 tests failed out of 23
Total Test time (real) =   5.94 sec
```

That includes the GUI-level targets — `settings_roundtrip, series_filter, error_paths,
measurements, mpr, help_search, series_summary, annotations, cine, export, dicomweb,
server_dialog` — not just the core ones. So interaction, view-state, and scan-flow units can be
verified on this host. Rendering *appearance* still cannot: a passing offscreen test proves the
code path runs, not that the result looks right.

## Not verifiable from here

- Whether `QOpenGLWidget::grabFramebuffer()` produces usable pixels under the offscreen plugin —
  unit 4b's golden-render test must check this first and fall back to a `QImage` paint path if it
  does not.
- Windows and macOS builds. Windows CI (`windows-app.yml`) remains the only Windows signal.
- Anything about the radiologist's own machine.
